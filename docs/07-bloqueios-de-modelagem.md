# 07 — Bloqueios de modelagem

Os problemas em [06](06-ingestao-e-staging.md) se resolvem no ETL. **Estes não.**
São incompatibilidades entre o modelo dimensional e as fontes que exigem
**mudança de DDL** — e portanto uma decisão antes de escrever o ETL.

Ordenados por gravidade.

---

## 1. `fat_vendas` — PK incompatível com o grão

### O problema

A tabela tem `sk_produto`, logo o grão é **item de venda**. Mas a PK é
`id_venda`:

```sql
CONSTRAINT pk_fat_vendas PRIMARY KEY (id_venda)
```

Uma venda com 3 produtos diferentes precisa de 3 linhas — e as 3 teriam o mesmo
`id_venda`. A PK rejeita.

Os números das fontes:

| Fonte | Vendas | Itens | Itens/venda |
|---|---:|---:|---:|
| Salvador | 900 | 3.166 | 3,5 |
| Itabuna | 500 | 1.757 | 3,5 |
| Feira | 500 | 1.698 | 3,4 |
| **Total** | **1.900** | **6.621** | **3,5** |

Com a PK atual cabem **1.900 linhas de 6.621** — e mesmo essas não caberiam,
porque há um segundo problema: **`id_venda` colide entre as lojas**. As três
fontes numeram vendas a partir de 1 (Itabuna e Feira via `SERIAL`/sequencial,
Salvador explicitamente). O `id_venda = 1` existe três vezes.

Ou seja: na prática cabem ~900 linhas das 6.621, e as outras falham por violação
de PK.

### Correções possíveis

**(a) Surrogate key própria — recomendada.** É o padrão Kimball para fato de
grão de item:

```sql
ALTER TABLE fat_vendas DROP CONSTRAINT pk_fat_vendas;
ALTER TABLE fat_vendas ADD COLUMN sk_venda bigint GENERATED BY DEFAULT AS IDENTITY;
ALTER TABLE fat_vendas ADD CONSTRAINT pk_fat_vendas PRIMARY KEY (sk_venda);
-- id_venda passa a ser dimensão degenerada (o número do pedido na origem)
ALTER TABLE fat_vendas ALTER COLUMN id_venda DROP NOT NULL;  -- opcional
```

Mantém `id_venda` como **dimensão degenerada** — útil para agrupar itens do
mesmo pedido e para rastrear até a origem. Precisa então de uma coluna de fonte
(ou usar `sk_loja`, que já identifica a origem) para que `(sk_loja, id_venda)`
volte a ser único.

**(b) PK composta pelo grão real:**

```sql
ALTER TABLE fat_vendas DROP CONSTRAINT pk_fat_vendas;
ALTER TABLE fat_vendas ADD CONSTRAINT pk_fat_vendas
    PRIMARY KEY (sk_loja, id_venda, sk_produto);
```

Mais enxuto, e a PK passa a **declarar o grão** — vantagem real de
documentação. Risco: se um pedido puder ter o mesmo produto em duas linhas
(dois preços, duas promoções), a PK rejeita. Nas fontes atuais isso não ocorre,
mas é uma restrição a mais.

**(c) Mudar o grão para venda** — remover `sk_produto` e agregar por pedido.
Descarta a análise por produto, que é provavelmente o ponto central do trabalho.
Não recomendada.

> **Recomendação:** (a). É a mais convencional, preserva a rastreabilidade e não
> impõe restrições sobre a estrutura dos pedidos.

## 2. `fat_concorrente` — fonte incompatível com o modelo

### O problema

A tabela exige:

| Coluna | Exigência |
|---|---|
| `sk_produto` | `NOT NULL`, FK para `dim_produto` |
| `quantidade` | `NOT NULL`, `CHECK >= 0` |
| `data` | `NOT NULL`, `date`, FK para `dim_data` |

A fonte (`08_Vendas_Concorrente.xlsx`) tem **três colunas**: `Ano`, `Mês`,
`Vendas (R$)` — 24 linhas de faturamento mensal agregado.

Ela **não tem produto**, **não tem quantidade** e **não tem dia**. Três das
cinco colunas da tabela não existem na fonte, e todas as três são obrigatórias.

Não há transformação honesta que preencha isso. Ratear R$ 185.000 de janeiro/2024
entre 17 produtos e inventar quantidades produziria dados fabricados
apresentados como medidos — exatamente o que não se deve fazer num DW.

### Correções possíveis

**(a) Redesenhar como fato agregado mensal — recomendada.** Aceitar que o
concorrente tem grão diferente:

```sql
DROP TABLE fat_concorrente;

CREATE TABLE fat_concorrente (
    ano          smallint       NOT NULL,
    mes          smallint       NOT NULL CHECK (mes BETWEEN 1 AND 12),
    valor_venda  numeric(14,2)  NOT NULL CHECK (valor_venda >= 0),
    CONSTRAINT pk_fat_concorrente PRIMARY KEY (ano, mes)
);
```

24 linhas, grão explícito, zero coluna inventada. A PK declara o grão e impede
duplicata — que a tabela atual, aliás, permite (não há `UNIQUE (data, sk_produto)`).

O custo: perde-se a FK para `dim_data`. Comparar com `fat_vendas` passa a exigir
agregação por mês — que hoje é impossível, porque `dim_data` não tem mês (ver
bloqueio 3). Os dois andam juntos.

**(b) Manter a FK para `dim_data`** usando o primeiro dia do mês como
representante, e remover `sk_produto`/`quantidade`:

```sql
CREATE TABLE fat_concorrente (
    data         date           NOT NULL REFERENCES dim_data(data),  -- sempre dia 1
    valor_venda  numeric(14,2)  NOT NULL CHECK (valor_venda >= 0),
    CONSTRAINT pk_fat_concorrente PRIMARY KEY (data)
);
```

Preserva a integração com `dim_data` ao custo de uma convenção implícita ("dia 1
representa o mês"), que precisa de `COMMENT` para não virar armadilha.

**(c) Manter a tabela como está e não carregar o concorrente.** Descarta a
análise competitiva. Se a comparação com o concorrente é requisito do trabalho,
não serve.

> **Recomendação:** (b) se `dim_data` ganhar a coluna `mes` (bloqueio 3),
> (a) se não ganhar.

## 3. `dim_data` — sem mês

### O problema

A dimensão tem só `ano` e `quadrimestre`:

| Coluna | Tipo |
|---|---|
| `data` | `date` (PK) |
| `ano` | `smallint` |
| `quadrimestre` | `smallint`, `CHECK 1..3` |

A posição 3 foi removida — era provavelmente `mes` ou `trimestre`.

Consequências:

1. **Análise mensal das vendas é impossível** sem derivar de `data` na query
   (`EXTRACT(MONTH FROM data)`), o que funciona mas contraria o propósito da
   dimensão de calendário.
2. **A fonte do concorrente é mensal.** Não há nível de agregação comum entre
   `fat_vendas` (diário) e o concorrente (mensal) dentro da dimensão. A
   comparação — provável objetivo central da análise — não tem como ser feita
   por join de dimensão.
3. **Quadrimestre é uma granularidade incomum.** 3 períodos de 4 meses. Não é
   trimestre. Se a intenção era trimestre, o `CHECK 1..3` está errado (deveria
   ser `1..4`) e o nome também.

### Correção

```sql
ALTER TABLE dim_data ADD COLUMN mes smallint;
UPDATE dim_data SET mes = EXTRACT(MONTH FROM data);
ALTER TABLE dim_data ALTER COLUMN mes SET NOT NULL;
ALTER TABLE dim_data ADD CONSTRAINT dim_data_mes_check CHECK (mes BETWEEN 1 AND 12);
```

Barato, e faz `dim_data` cumprir o papel de dimensão de calendário. Como a
tabela está vazia, é só incluir a coluna no DDL antes de gerar o calendário.

Vale confirmar de passagem se **quadrimestre** é mesmo o que se quer, ou se era
trimestre.

## 4. `dim_produto` — chave natural sem fonte

### O problema

```sql
CREATE UNIQUE INDEX ux_produto_atual ON dim_produto (id_produto) WHERE flag_atual;
```

`id_produto` é chave natural **global**, mas o mesmo valor identifica produtos
diferentes em cada fonte. Detalhado em
[05](05-fontes-de-dados.md#colisão-de-chaves-naturais-de-produto).

### Duas leituras possíveis

**(a) O modelo está correto e a conformação é obrigatória.** `id_produto` é a
chave do **catálogo conformado** (17 produtos), não da fonte. O de-para vive no
staging (`stg.map_produto_origem`) e o DW nunca vê os IDs de origem.

Nada muda no DDL. É a leitura que faz mais sentido para um DW: o catálogo
unificado é justamente o que o DW agrega de valor.

**(b) Produtos são por loja.** Aí falta uma coluna de fonte na dimensão, e a
chave natural passa a ser composta:

```sql
ALTER TABLE dim_produto ADD COLUMN fonte text NOT NULL;
DROP INDEX ux_produto_atual;
CREATE UNIQUE INDEX ux_produto_atual ON dim_produto (fonte, id_produto) WHERE flag_atual;
ALTER TABLE dim_produto DROP CONSTRAINT ex_produto_per;
ALTER TABLE dim_produto ADD CONSTRAINT ex_produto_per
    EXCLUDE USING gist (fonte WITH =, id_produto WITH =, tsrange(data_inicio, data_fim) WITH &&);
```

Isso multiplica a dimensão (47 linhas em vez de 17) e **impede comparar vendas
do mesmo produto entre lojas** sem um nível de conformação acima. Perde o
principal.

> **Recomendação:** (a) — não mudar o DDL, e tratar a conformação como
> responsabilidade explícita do staging. Registrar isso num `COMMENT` na coluna,
> para que a natureza global da chave não se perca:
>
> ```sql
> COMMENT ON COLUMN dim_produto.id_produto IS
>   'Chave natural do catalogo CONFORMADO (17 produtos), nao o id da fonte. '
>   'De-para por fonte em stg.map_produto_origem.';
> ```

## 5. Serviços sem destino

Itabuna tem 300 atendimentos de serviço (`atendimento_servico`) com receita real
— banho, tosa, consulta veterinária, vacinação, exame laboratorial. **Não existe
tabela de destino no DW.**

Três caminhos:

**(a) Criar `fat_servico`.** Grão: um serviço prestado a um cliente numa data.
Precisa de uma `dim_servico` (7 linhas). Só Itabuna tem serviços, então o fato
teria dados de uma loja só — o que é legítimo, mas limita a análise comparativa.

**(b) Deixar de fora e registrar a exclusão.** Defensável se o escopo do
trabalho é venda de produtos. O importante é **documentar**, para que a receita
total do Itabuna no DW não seja lida como a receita total da loja.

**(c) Tratar serviço como produto.** Carregar os 7 serviços em `dim_produto`
com categoria `Serviços` e os atendimentos em `fat_vendas`. Barato e permite
comparação direta produto/serviço — mas mistura conceitos e distorce qualquer
análise de catálogo de produtos.

> **Recomendação:** (b) para o escopo atual, com a exclusão documentada; (a) se
> a análise de serviços fizer parte dos objetivos.

## 6. Ausência de `dim_cliente`

Não é bloqueio — é escopo. Mas vale a decisão explícita.

As três fontes trazem `nome`, `email`, `telefone`, `sexo`, `data_nascimento`.
O modelo descarta tudo, mantendo só `estado_civil` degenerado em `fat_vendas`.

Perde-se: análise por gênero, por faixa de idade, recência/frequência por
cliente, ticket médio por cliente, curva ABC de clientes.

Se qualquer uma dessas análises está nos objetivos, `dim_cliente` precisa
existir — e aí a colisão de `id_cliente` entre fontes (200 + 100 + 130, todos
começando em 1) exige o mesmo tratamento de conformação dos produtos.

Uma nota sobre a qualidade desse dado, caso ele seja incorporado: `sexo` não
tem correlação com o nome nas fontes (o cliente 1 da Feira, `João Costa`, está
marcado como `Feminino`). Os dados são sintéticos, e análise demográfica sobre
eles produz resultados sem significado real. Ver
[05](05-fontes-de-dados.md#qualidade--é-a-fonte-mais-limpa).

## Resumo

| # | Bloqueio | Gravidade | Muda DDL? | Recomendação |
|---|---|---|---|---|
| 1 | `fat_vendas` PK vs. grão | **Bloqueante** — cabem ~900 de 6.621 linhas | sim | Surrogate `sk_venda`, `id_venda` como dimensão degenerada |
| 2 | `fat_concorrente` vs. fonte | **Bloqueante** — 3 colunas obrigatórias não existem na fonte | sim | Redesenhar como fato mensal sem produto |
| 3 | `dim_data` sem mês | Alta — impede comparação com o concorrente | sim | Adicionar `mes`; confirmar quadrimestre vs. trimestre |
| 4 | `dim_produto` chave global | Média — resolvido pelo staging | não | Manter DDL, documentar via `COMMENT` |
| 5 | Serviços sem destino | Média — 300 transações descartadas | opcional | Documentar a exclusão, ou criar `fat_servico` |
| 6 | Sem `dim_cliente` | Escopo | opcional | Decidir conforme os objetivos da análise |

Os bloqueios 1, 2 e 3 precisam ser resolvidos **antes** de escrever o ETL — eles
mudam a forma das tabelas de destino. Como o banco está vazio, o custo de
alterar agora é praticamente zero.
